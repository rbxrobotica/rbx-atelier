Como construir o sistema da Informat

31 de outubro de 2026 · Entrega 1 aprovada · base de engenharia: Informat Design System de 10/10/2026

A marca está fechada. O que falta decidir é a arquitetura do sistema: onde mora a fonte única, como o site estático consome os componentes sem carregar React, e o que fazer com o artefato de 10/10. As três direções abaixo partem do mesmo inventário e do mesmo reaproveitamento; mudam a forma de entregar.

Decisão · 1 de novembro de 2026

Direção 1, com SvelteKit no lugar de React

O proprietário escolheu o trilho duplo e trocou React por SvelteKit (D-19 em marca/decisoes.md). Onde esta prancha diz "React fino", leia "Svelte 5 fino": os componentes são arquivos .svelte sem estilo próprio, compondo as classes de bundle.css; o bundle.js do artefato sai do Vite em modo biblioteca com o runtime do Svelte embutido; o site é SvelteKit pré-renderizado com adapter-static, sem JavaScript nas páginas que não precisam dele. A direção 2 deixa de existir como alternativa (o site já é Svelte); a 3 continua descartada.

1

cópia, no artefato

Não há repositório nem o gerador de tokens local. Em qualquer direção, o primeiro passo é trazer os arquivos para ~/rbx/informat/design-system/.

Mapa completo, componente a componente e token a token: design-system/mapa-reaproveitamento.md. Resumo: 10 componentes mantidos ou re-skin, 10 arquivados (os de ordem de serviço), 9 novos.

DIREÇÃO 1

Trilho duplo: CSS primeiro, React por cima

Recomendada

A fonte única é uma pasta no repositório: tokens, CSS, bundle React, prévias e docs. O site usa só o CSS e um JavaScript mínimo; o React serve o artefato do design system e qualquer app futuro. Artefato novo "Informat Design System"; o de 10/10 fica arquivado.

Fluxo

tokens.json→ tools/tokens.py →tokens.cssinf.cssDTCG
tokens.css+bundle.css (inf-*)→site estático: HTML + site.js (menu, acordeão, validação)
bundle.css+bundle.js (React fino)→artefato Design System: prévias, README, cover
origem-2026-10-10/ (consulta)artefato de 10/10 (arquivado)

O bundle React só compõe as classes do CSS; o README de cada componente mostra a marcação HTML equivalente, que é a que o site usa.

Esforço médio

Prós

  • Cumpre o briefing do site: estático, sem dependências além das fontes, rápido.
  • Cumpre o briefing do sistema: componentes React em bundle.js com tipos e prévias.
  • É o que o sistema de 10/10 já é por baixo: CSS por tokens e React fino. A migração é renomear, podar e re-skin.
  • Fonte única em arquivos: versionável, regerável, independente da página do artefato.
  • Artefato novo limpo, sem o conceito de OS misturado.

Contras

  • Dois caminhos de marcação (HTML à mão no site, React no sistema) podem divergir. Mitigação: a marcação de referência é documentada por componente e a prévia é a prova.
  • Interações do site (menu, acordeão, validação) são escritas em JavaScript simples, à parte do React.

Escolha se

Você quer o site mais leve possível e um sistema que sirva tanto ao site quanto a um app futuro, com tudo em arquivos no repositório.

DIREÇÃO 2

React de ponta a ponta, pré-renderizado

Mesma pasta e mesmo bundle, mas o site também é escrito em React e convertido em HTML estático por um passo de build (ReactDOMServer num contêiner Node). Uma só marcação para sistema e site.

Fluxo

tokens.json→tokens.cssbundle.cssbundle.js
páginas em React→ Node + ReactDOMServer (podman) →HTML estático
hidratação = React no site (45 KB gzip)ousite.js em JavaScript simples, do mesmo jeito

O ganho de "uma só marcação" só vale se o site hidratar; sem hidratar, as interações voltam a ser JavaScript à parte.

Esforço alto

Prós

  • Prévias do sistema e páginas do site são o mesmo código.
  • Menos risco de a marcação do site divergir dos componentes.

Contras

  • Acrescenta uma toolchain (Node, pré-render) para um site de seis páginas; a máquina local não tem Node, só podman.
  • Com hidratação, o site carrega React e fere "sem dependências de terceiros"; sem hidratação, o JavaScript das interações é escrito à parte do mesmo jeito.
  • Publicar no Nginx passa a depender do build; editar um texto exige regerar.

Escolha se

O site vai crescer para uma aplicação (área do aluno, acompanhamento) e o custo da toolchain se paga.

DIREÇÃO 3

Revisar o artefato de 10/10 no lugar

Editar o artefato existente: trocar tokens, logo, fontes e textos, manter os 21 componentes (inclusive os de ordem de serviço) e acrescentar os novos. O artefato continua sendo a fonte; o site consome o CSS como na direção 1.

Fluxo

artefato de 10/10 (editado ao vivo)→tokens, logo, README trocados
21 componentes antigos+9 novos→bundle de 30 componentes
sem repositório: a página é a única cópia
Esforço baixo no começo

Prós

  • Menor esforço inicial; mantém a URL e o histórico de versões.
  • Os componentes de atendimento ficam disponíveis para um app futuro.

Contras

  • O conceito de OS e "um produto RBX" permanece em dez componentes e nos textos; o sistema fica com duas identidades.
  • Bundle maior do que o site usa; mais superfície para manter.
  • A única cópia continua sendo a página: um erro numa edição ao vivo não tem volta sem repositório.
  • O briefing pede um sistema da marca aprovada; este seria um sistema de outra marca com a pele trocada.

Escolha se

Um app de atendimento com ordem de serviço está nos planos de curto prazo e vale mais que a clareza do sistema.

Recomendação

Direção 1 · Trilho duplo

O sistema de 10/10 já é, por dentro, CSS por tokens com React fino por cima. A direção 1 só torna isso explícito e tira o site da dependência do React, que é o que o briefing pede. A direção 2 compra complexidade que um site de seis páginas não paga; a direção 3 economiza uma semana e cobra em clareza pelo resto da vida do sistema.

Ordem de trabalho, se aprovada: trazer os arquivos restantes do artefato de 10/10 para a pasta; escrever tokens.json e o gerador; migrar o CSS e o bundle (renomear, podar, re-skin); escrever os nove componentes novos com README e prévia; criar o artefato "Informat Design System" a partir do tipo e publicar; montar as telas de aprovação nos dois temas.

Pendências para você

  1. Direção: 1, 2 ou 3. bloqueia a Entrega 2
  2. Artefato de 10/10: posso renomeá-lo para "Informat Design System · Placa (arquivado)" para não confundir com o novo? Nada mais muda nele. Padrão se não responder: não renomeio.
  3. Rodapé e RBX (pendência 3 da Entrega 1): o Footer nasce sem "um produto RBX". Confirme ou peça a linha.
  4. Área logada ou login no site: o briefing não tem. Padrão: nenhum "Entrar" na NavBar.
  5. Mono para apostilas: pilha do sistema (padrão) ou uma mono do Google Fonts (JetBrains Mono, Atkinson Hyperlegible Mono)?
